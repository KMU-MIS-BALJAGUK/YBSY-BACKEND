# Flyway 마이그레이션

## 파일 이름: 날짜·시간 버전

```
V{yyyyMMddHHmm}__{설명}.sql
예) V202611261530__create_users_and_profiles.sql
    V202611261531__create_refresh_tokens.sql
```

- 버전은 **파일을 만든 시각**(연·월·일·시·분, 12자리)으로 쓴다. 밑줄은 두 개(`__`).
- 설명은 영어 소문자 + 밑줄, 무엇을 하는지 동사로 시작한다(`create_`, `add_`, `alter_`, `drop_`).
- 한 PR에서 여러 파일을 만들면 실행 순서대로 분 단위를 1씩 올린다.
- `V1`, `V2`처럼 순번을 쓰지 않는다. 세 명이 동시에 작업하면 같은 번호가 생겨 서버가 뜨지 않는다.

## 지킬 것

- 한 번 `main`에 머지된 파일은 **절대 수정하거나 이름을 바꾸지 않는다.** 고칠 게 있으면 새 시각으로 파일을 추가한다(`ALTER TABLE ...`).
- 아직 머지 전인 내 브랜치의 파일은 고쳐도 된다. 대신 로컬 DB에 이미 적용됐다면 로컬 DB를 초기화한다(`docker compose down -v` 후 `docker compose up -d`).
- **다른 담당의 테이블을 만들지 않는다.** 필요한 테이블이 아직 없으면 담당자 PR이 먼저 머지되기를 기다리거나 담당자와 순서를 정한다. 담당은 `docs/MIGRATION.md` 4장.
- MySQL 8 문법으로 작성한다. 원본(Supabase PostgreSQL)과의 차이는 `docs/MIGRATION.md` 참고.

## 순서가 뒤바뀌어 머지될 때

내가 10시에 만든 파일보다 다른 사람이 9시에 만든 파일이 나중에 머지될 수 있다. 이때 내 로컬 DB에는 10시 파일이 이미 적용돼 있어서, Flyway는 기본적으로 "더 이른 버전이 새로 나타났다"며 서버 실행을 막는다.

그래서 `local` 프로필은 `spring.flyway.out-of-order: true`로 이런 파일도 실행하게 해 두었다. 서로 다른 테이블을 다루는 한 순서가 바뀌어도 문제없다. 같은 테이블을 건드리는 파일끼리는 머지 순서를 미리 맞춘다.
